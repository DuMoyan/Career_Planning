# AI智能体大学生职业生涯规划系统 MVP设计

## 1 项目意图

本项目依据《基于AI智能体大学生职业生涯规划系统 软件项目需求定义书》建设一个可部署、可演示、可测试的标准全栈 MVP。系统面向高校大四学生，帮助学生完成自我探索、能力证据整理、目标比较、差距分析、规划生成、任务执行和周度复盘，形成一条完整但收敛的生涯规划闭环。

MVP不是测评后直接给出职业结论的工具。兴趣、人格或行为倾向、职业价值观、能力证据和目标要求必须分开存储与展示；AI输出只能作为可修改的建议，未经学生确认不得激活为正式计划。

## 2 成功标准

学生可以在一套本地或服务器部署的 Web 系统中完成以下端到端流程：

1. 使用演示账号登录并维护个人档案和现实约束。
2. 完成职业兴趣和职业价值观测评，查看带来源、版本、日期和局限说明的报告。
3. 上传简历或手工添加经历，将解析结果确认为能力证据并生成能力画像。
4. 从岗位库选择至少两个目标，并比较硬性门槛、可补足要求、未知项、兴趣与价值观线索以及能力差距。
5. 输入每周可投入时间后生成结构化规划草案；检查依据、未知项和风险，修改并确认激活。
6. 查看里程碑和周任务，完成打卡、耗时记录和证据回填。
7. 查看自然周统计和复盘建议，并选择采纳、修改或拒绝调整建议。
8. 系统在未配置或无法访问大模型时仍能通过规则模板完成上述核心演示。

## 3 MVP范围

### 3.1 包含功能

#### M1 用户与权限

- 学生、导师、管理员三类演示账号的登录、刷新令牌和退出。
- 服务端 RBAC 与资源归属校验，学生只能访问本人数据。
- 学生基础档案、专业背景、每周可投入时间和现实约束维护。
- 导师授权数据模型和撤回接口；MVP界面仅提供学生侧授权管理和最小导师只读验证页。
- 登录、授权变更、计划激活和关键配置变更的追加式审计日志。

#### M2 职业测评与自我探索

- 内置自编演示版 RIASEC 兴趣题目和职业价值观题目，明确标注为教学演示、非诊断工具。
- 分段答题、进度暂存、返回修改、提交确认和幂等提交。
- 按量表版本计分并保留历史报告。
- 兴趣与价值观分别展示，不合并为单一职业适配分。
- 报告展示量表版本、完成日期、数据来源、解释边界和局限。
- 工作环境偏好和学生反思记录。

人格或行为倾向量表只保留扩展接口和页面说明，不在 MVP 中内置具体量表，以规避版权和适用性风险。

#### M3 简历解析与能力画像

- 支持 PDF、DOCX 和 TXT 简历上传，单文件不超过 10 MB。
- 提取文本并基于关键词和章节规则生成经历与技能草稿。
- 解析结果必须由学生核对、修改和确认后才能转为能力证据。
- 支持手工新增课程、项目、竞赛、实习、证书和自评证据。
- 按证据数量、来源类型和确认状态生成可解释的能力画像。
- 保留画像版本并支持查看当前版本与上一版本的变化。

MVP不追求通用高精度 NLP 简历解析，也不调用外部招聘平台或学籍接口。

#### M4 目标岗位库

- 提供有限的演示岗位种子数据，包括软件开发、数据分析、产品经理和算法工程等方向。
- 每个岗位记录能力要求、硬性门槛、可补足要求、来源、采集日期、核验日期和有效状态。
- 支持关键词和类别检索。
- 暂不实现升学院校库的完整维护界面，仅预留统一目标模型的 `program` 类型。

#### M5 目标比较与规划智能体

- 学生可选择 2 至 3 个目标，设置优先级、价值权重和现实约束。
- 对目标逐项展示已满足、待补足、未知和硬性门槛状态。
- 缺失数据标记为未知，不按零分处理。
- 每项判断可追溯到能力证据、测评结果或岗位来源。
- 规划工作流依次执行输入快照、目标要求检索、画像与约束分析、Gap 诊断、里程碑生成、周任务拆解、工时可行性检查和结构校验。
- 规划先保存为草稿；学生可以编辑、重新生成、拒绝或确认激活。
- 激活时通过单一事务创建计划版本、里程碑和任务。
- 重规划生成新版本，保留历史版本、变更原因、已完成任务和打卡流水。

#### M6 任务与打卡

- 任务按待办、进行中、已完成、延期和放弃管理。
- 支持预计耗时、截止日期、优先级、验收标准和来源依据。
- 打卡记录实际耗时、执行说明和可选证明链接。
- 重复打卡请求通过幂等键避免重复流水。
- 延期或放弃需要填写原因，可触发重规划建议。

#### M7 周报与动态迭代

- 按自然周聚合计划任务数、完成数、完成率、预计与实际投入时间。
- 基于确定性规则生成偏离提示，并可附加 AI 复盘建议。
- 调整建议必须支持采纳、修改和拒绝，不自动变更正式计划。

### 3.2 最小角色界面

- 学生端是完整 MVP 的主要交付对象。
- 导师端仅实现登录、查看已授权学生的目标/计划摘要和添加一条批注，用于验证授权边界。
- 管理员端仅实现岗位种子数据查看、量表版本查看和审计日志查看，用于验证 RBAC 和配置边界。

### 3.3 不包含功能

- 完整求职投递 Pipeline、面试日历、面试复盘和升学申请流程。
- 完整导师约谈、帮扶跟踪和就业中心统计大屏。
- 脱敏批量导出、正式备份恢复自动化和 500 在线用户容量承诺。
- 真实招聘平台、学校统一认证、教育部学籍或企业 HR 系统集成。
- 原生移动应用。
- 心理诊断、危机判断、录取概率承诺或唯一职业推荐。
- 未经许可的商业量表和题目。

上述能力保留清晰的数据与服务扩展点，但不进入首版页面和验收范围。

## 4 实现方案比较

### 方案一 标准全栈 MVP 已选

Vue 3 前端、FastAPI 后端、PostgreSQL 持久化、Redis 缓存与异步状态、兼容 OpenAI API 的模型适配器，以及规则模板降级。该方案最接近需求基线，可以验证权限、事务、版本和 AI 人工确认边界，并能自然扩展后续模块。

代价是工程结构和部署组件较多，首版必须严格控制页面和业务范围。

### 方案二 轻量演示版 未选

Vue 3 和 FastAPI 保留，但使用 SQLite、进程内任务和模拟 AI。启动更简单，但无法充分验证 PostgreSQL 约束、Redis 状态、异步任务和部署要求，后续迁移成本较高。

### 方案三 界面原型优先版 未选

优先制作全部页面并使用 Mock API。适合展示界面，但不能证明权限、事务、数据生命周期和完整业务闭环，不符合“开发相应程序”的目标。

## 5 系统架构

### 5.1 目录和运行单元

- `frontend/`：Vue 3、Vite、TypeScript、Vue Router、Pinia、Element Plus、Axios、ECharts。
- `backend/`：Python 3.11、FastAPI、Pydantic v2、SQLAlchemy 2.0 AsyncSession、Alembic、pytest。
- `backend/app/api/`：路由、请求解析和响应 DTO，不承载业务规则。
- `backend/app/services/`：认证、测评、画像、目标、规划、任务和周报用例服务。
- `backend/app/domain/`：状态机、计分、Gap 分类、计划校验等纯业务逻辑。
- `backend/app/agents/`：LangGraph 工作流、模型适配器、规则降级和结构化输出。
- `backend/app/repositories/`：数据访问接口和 SQLAlchemy 实现。
- `backend/app/models/`：数据库模型。
- `backend/app/schemas/`：API 与 Agent Pydantic 模型。
- `backend/tests/`：单元测试、权限测试、服务集成测试和关键 API 测试。
- `infra/`：Nginx、Dockerfile、Compose 和初始化配置。

Docker Compose 启动 `frontend`、`backend`、`postgres` 和 `redis` 四个核心服务。后台 AI 任务在 MVP 中由 FastAPI 后台任务与 Redis 状态配合执行；接口边界保持可替换为独立 Worker，避免首版额外引入复杂队列系统。

### 5.2 前后端交互

- 业务 API 采用 `/api/v1` 前缀。
- 普通 CRUD 使用 JSON REST API。
- AI 规划使用异步运行记录和 SSE：创建运行后返回 `run_id`，前端订阅进度事件并可停止订阅。
- SSE 断开不取消后端已提交工作；前端可使用 `run_id` 查询最终状态。
- 所有正式写入操作由后端再次校验身份、归属、状态和版本。

### 5.3 关键状态

- 规划：`draft -> active -> archived`，草稿也可进入 `discarded`。
- 任务：`todo -> in_progress -> completed`，或进入 `delayed`、`abandoned`。
- AI运行：`queued -> running -> succeeded|failed|cancelled`。
- 授权：`active -> revoked|expired`。

非法状态转换返回明确业务错误码，不依赖前端按钮控制。

## 6 数据设计

MVP核心表包括：

- `users`、`refresh_tokens`、`student_profiles`
- `mentor_grants`、`user_consents`、`audit_logs`
- `assessment_scales`、`assessment_items`、`assessment_records`、`assessment_answers`
- `career_preferences`
- `resume_files`、`experience_records`、`competency_evidence`、`competency_profiles`
- `target_positions`、`target_requirements`
- `career_goals`、`goal_targets`
- `career_plans`、`plan_versions`、`plan_milestones`
- `growth_tasks`、`task_checkins`
- `weekly_reports`
- `ai_generation_logs`
- `mentor_comments`

通用约束：

- 主业务表使用 UUID 主键，外键和唯一约束在数据库层实现。
- 所有用户数据包含归属字段和创建、更新时间。
- 关键来源数据包含 `source_type`、`source_ref`、`verified_status` 和数据时间。
- 测评记录绑定量表、计分规则和解释规则版本，历史结果不静默重算。
- AI 日志只保存必要的输入字段引用与版本，不默认保存完整答卷或简历原文。
- 审计日志为追加式，普通业务接口不提供修改和删除能力。
- 计划版本和打卡流水不做覆盖式更新。

## 7 AI与规则降级设计

### 7.1 模型适配器

定义统一的模型接口，接收结构化上下文并返回符合 Pydantic Schema 的规划或复盘结果。模型地址、模型名、密钥、超时和 Token 上限全部通过环境变量配置。

真实模型可用时，LangGraph 调用模型并执行：

1. 输入最小化和敏感字段过滤。
2. 目标资料检索。
3. 结构化生成。
4. Pydantic 校验。
5. 规则检查，包括总工时、截止日期、未知信息和禁止性结论。
6. 至多一次修复生成；仍失败则进入规则模板降级。

### 7.2 规则模板降级

未配置密钥、超时、限流或结构校验失败时，系统根据 Gap 项、目标截止日期和每周可用工时生成确定性的里程碑与任务：

- 硬性门槛优先于可补足要求。
- 未知项先生成“核实信息”任务。
- 单周预计总工时不得超过学生设置的可用工时。
- 每个里程碑至少有一个可验证验收标准。
- 所有模板内容明确标记为规则生成，不伪装成模型结论。

### 7.3 人工确认

AI 或规则输出只写入规划草稿和 AI 运行日志。只有学生点击确认激活后，后端才在事务内创建生效版本和任务。重新生成不会覆盖现有生效计划。

## 8 核心页面

1. 登录页：账号密码登录和演示账号提示。
2. 学生工作台：当前目标、画像摘要、本周任务、周进展和下一步行动。
3. 自我探索中心：量表列表、分段答题、历史报告、工作环境偏好和反思。
4. 简历与能力画像页：上传、解析草稿、证据确认、能力图表和版本变化。
5. 岗位与目标页：岗位检索、详情、目标选择和多目标并列比较。
6. AI 规划舱：约束设置、Gap 结果、生成进度、草稿编辑、依据和激活确认。
7. 任务看板：周任务、状态切换、打卡表单和延期/放弃原因。
8. 周报页：周统计、偏离提示和调整建议反馈。
9. 隐私与授权页：数据用途、共享范围、导师授权和撤回。
10. 最小导师页：授权学生列表、计划摘要和批注。
11. 最小管理页：岗位数据、量表版本和审计日志只读视图。

视觉采用需求书指定的深蓝 `#1E3A8A`、青绿 `#0D9488` 和暖橙 `#F59E0B`。PC 端使用顶部全局栏、左侧导航和主工作区；移动端保证查看与打卡核心操作可用。兴趣、价值观与能力图表分开呈现。

## 9 安全和隐私

- 密码使用 Argon2 或 bcrypt 加盐哈希。
- 访问令牌短期有效，刷新令牌以可撤销摘要形式存储。
- 登录失败实施按账号与来源地址组合的限流和临时锁定。
- 文件上传校验扩展名、MIME、大小和随机化存储名；解析失败不产生半写入证据。
- 服务端执行角色、资源归属和导师授权三层校验。
- API 错误不返回堆栈、数据库细节或模型密钥。
- 日志过滤认证头、密码、令牌、完整测评答案和简历原文。
- 撤回导师授权后立即拒绝后续访问，并使授权范围缓存失效。
- 示例数据与真实数据通过环境标识区分；种子数据不包含真实个人信息。

## 10 错误处理与可恢复性

- API 使用稳定的业务错误码和中文用户提示。
- 数据库写入在事务中执行；失败时不保留半成品。
- 幂等键覆盖测评提交、计划激活和任务打卡。
- AI 失败保留输入快照和错误摘要，允许重试或规则降级。
- 前端提供加载、空数据、错误和重试状态。
- 关键请求携带 `trace_id`，但日志不记录不必要的个人信息。

## 11 测试与验收

测试采用 pytest、Vitest 和必要的 Vue Test Utils。优先覆盖：

- 密码验证、令牌过期、账号锁定和跨用户访问拒绝。
- 授权范围、撤回后访问拒绝和敏感字段不返回。
- 量表版本计分一致、进度恢复和重复提交幂等。
- 简历解析结果未经确认不进入能力画像。
- Gap 分类中缺失数据为未知而非零分。
- 规划 Schema、工时限制、人工激活和规则降级。
- 规划重构保留历史版本、已完成任务和打卡流水。
- 任务状态机、重复打卡和周报聚合一致性。
- 前端关键页面的权限路由、错误态和核心交互。

MVP验收以以下自动化与场景结果为准：

- 后端核心业务逻辑测试通过，核心模块覆盖率目标不低于 65%。
- 前端构建成功，关键组件测试通过。
- Docker Compose 能在提供环境变量后启动四个核心服务。
- 使用种子账号完整演示成功标准中的八步流程。
- 未配置模型密钥时，规则降级流程仍可生成、激活和执行计划。

需求书中的 500 同时在线、100 QPS 和生产级备份恢复作为完整版本目标；MVP只执行基础接口与 50 并发关键写入的数据一致性验证。

## 13 实施约束和开发者裁量

必须遵守的约束：

- Python 3.11、Vue 3、PostgreSQL 14、Redis 7。
- 业务规则不放在 FastAPI 路由中。
- 生产代码使用测试驱动方式实现核心逻辑。
- AI 不得直接激活计划或修改正式任务。
- 兴趣、价值观、行为倾向和能力不得混为一个结论或图表。

开发者可以在不改变本设计范围的前提下决定：

- 具体组件拆分、文件命名和样式细节。
- PostgreSQL 字段长度、普通索引和非关键 DTO 命名。
- 图表类型和响应式断点。
- 使用 Argon2 或 bcrypt 的具体实现。
- 规则模板的中文文案，只要满足可追溯、非确定性和非诊断边界。

## 14 审阅后明确的设计决策

以下内容由设计者依据需求书中的可解释性、人工确认和 MVP 收敛原则确定，不要求开发阶段再次选择。

### 14.1 能力字典与 Gap 判定

MVP使用受控能力字典，不以自由文本直接参与匹配。能力项包含唯一编码、名称、类别和 0 至 4 级等级说明。首批类别为专业知识、编程开发、数据分析、研究分析、产品需求、沟通表达、团队协作、项目执行和外语能力；岗位可以引用任意能力项并声明要求等级、是否硬性、依据和核验日期。

学生确认能力证据时，需要选择能力项和可证明等级 1 至 4。简历解析只给出候选映射，不自行确认等级。证据来源同时标记为实习或正式项目、课程或科研、竞赛或证书、自主项目、自我评价；来源类型用于解释可信度，不通过叠加证据数量虚增能力等级。

当前能力等级取该能力项所有已确认且未删除证据中的最高可证明等级，并同时展示证据数量与来源。Gap 状态按以下顺序确定：

1. 无已确认能力证据时为 `unknown`。
2. 当前等级达到要求时为 `met`。
3. 当前等级不足且要求为硬性时为 `hard_unmet`。
4. 当前等级不足且要求非硬性时为 `developable_gap`。

兴趣与价值观仅作为目标比较线索，不改变上述能力 Gap 状态。

### 14.2 能力画像版本

能力画像由已确认能力证据确定性计算。首次生成画像，以及新增、修改、确认、取消确认或删除证据后由学生点击“更新画像”时，创建新版本；系统不在后台静默改写当前画像。画像保存各能力项当前等级、证据引用、数据完整度和生成时间。

学生不能直接覆盖计算后的能力等级。如结果不符合实际，应修改证据映射、证明等级或确认状态，再生成新版本。这样可以保留可解释性和完整历史。

### 14.3 目标与截止日期

学生比较 2 至 3 个目标后，需要选定一个主目标才能生成计划；其他目标作为备选继续保留，但不混入同一份任务计划。每个目标由学生分别填写目标截止日期、每周可用工时、地点和资源约束。截止日期是计划生成的必填项，不从岗位资料推断。

同一时间每个职业目标只能有一个生效计划版本。不同目标可各自保留计划，但学生工作台只突出当前主目标的生效版本。

### 14.4 重规划与任务迁移

重规划在同一个 `career_plan` 下创建新的 `plan_version`。学生确认新版本后，旧生效版本在同一事务中变为 `archived`，新版本变为 `active`。

任务归属于明确的计划版本。旧版本的已完成任务和全部打卡始终保留，不复制到新版本；新版本通过历史摘要引用这些成果。旧版本的未完成任务由重规划结果列出“继续、替换、取消”建议，学生在激活前确认。选择继续的任务会以新任务记录复制到新版本，并通过 `source_task_id` 关联原任务；旧任务随旧版本归档，不再接受打卡。

### 14.5 周报建议处理

- `accept`：基于该建议创建一个重规划草稿和新的 AI 运行，不立即修改生效计划。
- `modify`：学生先编辑建议内容，再创建重规划草稿。
- `reject`：只记录拒绝状态和可选原因，不触发规划变更。

无论采纳还是修改，都必须经过重规划预览和计划激活确认。

### 14.6 演示量表基线

MVP内置项目原创的教学演示题库：RIASEC 共 36 题，每个维度 6 题；职业价值观共 21 题，覆盖成长成就、自主性、稳定保障、经济回报、社会贡献、人际协作和工作生活平衡 7 个维度，每个维度 3 题。题目统一采用 1 至 5 级同意度选项，MVP不设置反向题。

各维度按题目均值线性换算到 0 至 100 分。报告展示完整维度结果和前三项相对偏好，同时明确“分数仅用于自我探索，不代表能力、诊断或职业结论”。题库、计分和解释分别带版本号；后续修改只能发布新版本。

### 14.7 导师授权与批注

授权范围采用三个可独立选择的数据类别：`profile_summary`、`goals`、`plan_progress`。原始测评答案、简历原文和私人 AI 输入永不属于 MVP 导师授权范围。授权必须填写到期时间，默认 90 天，学生可提前撤回。

导师批注附着于具体计划版本，学生可见并可标记已读；批注不可修改学生计划。授权撤回或到期后，导师不能继续读取计划或批注上下文，但历史批注对学生和审计记录保留。

### 14.8 AI运行并发与重试

MVP不提供已经开始执行的服务端硬取消。前端“停止”仅停止 SSE 展示，运行仍可通过 `run_id` 查询。AI运行状态收敛为 `queued -> running -> succeeded|failed`。

同一学生同一时间最多有一个 `queued` 或 `running` 的规划运行；重复发起返回 409 和现有 `run_id`。失败后重试或主动重新生成都创建新的运行记录和输入快照，并通过 `retry_of` 或 `regeneration_of` 引用原运行，不覆盖历史结果。

### 14.9 简历文件生命周期

MVP将原文件保存在 Docker 持久卷中，通过文件存储接口访问，目录路径和文件名不直接暴露给客户端。接口设计允许后续替换为对象存储。

原文件在学生主动删除前保留。学生删除原文件后，文件内容和下载能力被移除，元数据保留删除时间以供审计；已经由学生确认的经历和能力证据继续保留，但其来源显示为“原文件已删除”。未确认的解析草稿随原文件删除。删除动作不静默重算历史画像。

### 14.10 并发一致性验证

50 并发关键写入验证覆盖两类操作：

1. 对同一计划草稿使用同一幂等键并发激活，最终只能存在一个生效版本和一组任务。
2. 对同一任务使用同一幂等键并发打卡，最终只能新增一条打卡流水并发生一次状态更新。

成功标准是无重复记录、无部分写入、无未处理服务器错误，最终数据库状态与单次成功请求一致。MVP不为该验证额外承诺延迟指标。
